约3,600,002字符、100,000行JSON；下表为热身后3轮中位数，连续20次编辑的每键CPU路径耗时（含反射调用，不是GPU帧时间）。

首次编辑单独测量：新版普通输入在开头/中间/末尾分别约1.911 / 1.453 / 0.764ms，各分配约7,202,272字节。它初始化可变缓冲区，不是零分配；后续操作复用缓冲区。约36k字符的小文件连续普通输入也改善，原版约0.048–0.051ms/键，新版约0.0046–0.0151ms/键。

搜索开启时连续输入约从6.2–12.0ms/键降到0.002–0.352ms/键，主要来自把重复搜索改为停止输入后刷新。不能将它解读为全文搜索本身变快或不再需要全文快照。

单次headless进程顺序对照，不是多机型统计结论；测量覆盖开头/中间/末尾，未用末尾最佳值概括所有位置。远距离切换编辑位置会有gap移动成本。

## 改动目的与边界

保留现有自绘编辑器，不引入 AvaloniaEdit、Monaco 或新的生产 NuGet 依赖。解决普通输入生成全文字符串、重建全部行索引，并经双向 Text 绑定同步全文的问题。

- `JsonTextBuffer`：UTF-16 gap buffer。查看时复用原始字符串；首次编辑才分配可变数组。局部连续输入复用空隙，不生成全文字符串。远距离移动编辑位置会移动 gap 内的字符，容量不足会增长，不能承诺每次输入常数时间。
- `JsonTextSource`：提供统一只读字符访问，语法分析、光标定位、绘制和自动缩进直接读取原文或缓冲区，不先调用 ToString。
- `JsonTextDocument`：重新解析编辑范围及相邻行，正确处理 CRLF 合并/拆分和 Unicode 列宽；维护修改状态与显式字符串快照。
- 仍采用紧凑的平面行表，插入/删除改变长度时调整后续行偏移。它不是平衡树，开头编辑仍有 O(后续行数) 的元数据工作，但不重新扫描后续正文或分配全文副本。最长行缩短时可能重新检查行宽表。
- `ProfilesViewModel.ConfigDocument` 与编辑器共享文档；不再每次输入回写完整字符串。原 `ConfigContent` 保留为保存、格式化、校验、外部内容赋值和新建表单使用的快照接口。
- 未保存状态对等长编辑增量计算；内容长度不同直接判断为修改。当长度重新回到保存版本且比较状态失效时，可能执行一次不分配字符串的内容比较，确保手动还原和撤销返回干净状态正确。
- 撤销重做直接应用增量记录，不走全文重建。保存后仍可撤销；格式化/重新加载视为外部文档替换并清理旧历史，与原有行为一致。
- 搜索开启时，编辑立即失效旧匹配，停止输入约150ms后重新搜索，不把全文搜索放在每次按键的同步路径。刷新不移动正在输入的光标。实际搜索仍需全文快照/遍历，并非取消这部分成本。
- 控件脱离窗口时退订文档事件，重新挂载时检测版本变化并清理失效历史，防止文档保留已关闭编辑器。

## 正确性验证

- Gap buffer 15,000 次随机编辑，对照不可变字符串：替换、删除、插入、边界、Unicode、CR/LF、切片、快照缓存。
- 行索引/修改状态 12,000 次随机替换，每次对照完整行扫描与原文比较，包括断开的代理项和 CRLF。
- 文本仅查看时不分配全文副本；大文件预热后500次局部输入不产生文档级分配。
- 真实编辑器：输入、Unicode删除、回车缩进、选区替换、撤销重做、只读入口、12种延迟剪贴板场景、正则超时与恢复。
- 挂载与生命周期：搜索刷新不抢光标、脱离期间重新加载、文档切换、文档保持存活时旧编辑器可回收。
- 使用真实 ProfileManager / ConfigManager 和独立临时文件测试：编辑后的保存状态、撤销回基线、磁盘保存、保存后撤销/重做、格式化、语法校验、退出清理。实际打开未保存对话框并触发“取消／不保存／保存”：取消保留编辑状态，不保存保持磁盘文件不变，重新打开加载原内容，保存并退出写入最新内容。测试初始化曾错误地在应用初始化后配置生命周期，修正为初始化时设置后全部通过；产品代码没有因此改动。
- 真实桌面亮暗主题和700/900宽度截图；配置列表虚拟化/双向键盘/回收回归。

先前完整测试曾出现一次既有 `WindowMaterialTests` 临时配置写入拒绝访问；未改动该逻辑，保留失败日志，随后完整复跑400项通过，新增惰性加载断言后的最终401项也通过。

## 测量口径

对照原版源码快照 `artifacts/json-editor-refresh/source-before` 与最终源码，Release相同运行环境。使用真实自绘控件和方法；headless排除GPU，不能当作真实帧率或端到端显示延迟。

输入覆盖1,000/100,000行（约36k/3.6m字符）的开头、中间、末尾，各有普通输入、回车和搜索开启时输入。每组预热一次，再测3轮，每轮区分首次编辑与后续20次编辑。统计分配在任何全文导出/检查之前截取。基线编辑器回车只插入换行；新版会按上下文缩进，因此回车插入字符数可能不同。

搜索开启的连续输入指标不包括停止输入后那次延迟搜索；相关延迟刷新正确性单独验证。首次编辑必须显式报告缓冲区初始化成本，不能只报热路径。

保留托管内存测试在独立诊断进程中强制回收以比较存活对象，不是工作集节省测量，也不向产品加入GC或trim。两版都保持原始内容字符串存活，模拟配置的保存基线，分别记录加载、首次编辑、501次编辑和替换为小文档后的额外托管内存。未测GPU显存。

包体使用相同NativeAOT参数发布并比较exe及目录总大小；基线为本轮编辑器改动前的源码，因此差值包含本轮可靠性/自动缩进/UI调整，不能全部归因于gap buffer。

## 剩余边界

没有大型文本树；远距离跳转后的第一次修改、极长单行、大段粘贴、gap增长仍可能有较大工作量。当前只对局部编辑和真实约3.6m字符文档提供实测结论，不承诺任意大小JSON恒定延迟。全文保存/格式化/搜索仍需要完整内容；中文IME组合输入、屏幕阅读器和多机型GPU未做专项认证。
