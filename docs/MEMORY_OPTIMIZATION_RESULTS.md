# carton 内存优化结果

对齐任务管理器默认「内存」列 = **专用工作集**。不是提交大小，也不是工作集。

剖析过程、证伪项、测量脚本见 [`MEMORY_OPTIMIZATION_REPORT.md`](./MEMORY_OPTIMIZATION_REPORT.md)。

**「0 个配置约 50MB / 8 个配置约 70MB」是一打开 carton（内核未启动）的任务管理器「内存」。**
不是启动内核。打开时配置正文不应进内存；只有点进编辑、或点启动做覆写时才读盘，用完释放。

---

## 结果（空闲、默认 GPU、窗口在）

| 列 | 现在 |
|---|---|
| **内存（专用工作集）** | **约 20–22 MB** |
| 工作集 | 约 60 MB |
| 提交大小 | 约 180–190 MB（NVIDIA 驱动映射，共享为主） |

早期 carton 启动「大约 40MB」也是「内存」列的量级。现在空闲不比那时差。

强制软件渲染能把提交大小打到约 40MB，专用工作集本来就约 20MB，对你看的那一列几乎没帮助，已撤回，渲染保持 Avalonia 默认。

---

## 怎么做到的（对「内存」列真正有用的）

1. **页面按需加载，离开约 1 分钟卸界面 VM**  
   连接 / 配置 / 设置 / 日志页不常驻整棵可视化树。任务管理器「内存」看的是还活着的私有页。

2. **日志有独立数据层，卸页不会清历史**  
   `LogStore` 在 `MainViewModel` 里进程级常驻，环形最多 800 条。日志页只是视图。离开再进，仍从 Store 快照画出来。内核日志在人不在该页时也会继续写入 Store。连接/配置没有这种仓库，卸了就卸了。

3. **`MemoryOptimizer` 以前是空操作**  
   非法的 `Aggressive + blocking:false` 抛错被吞，回收和 Trim 从没跑。现在卸页、隐到托盘、停内核后才会把已经死掉的私有页还给系统——这是「内存」列会掉的直接原因。

4. **缓冲和订阅封顶**  
   日志环 800；下载内存队列 16MB 且 `DownloadService` 用完 Dispose；后台页不空转 UI 订阅。防的是用一阵再看任务管理器已经很大。

5. **少加载**  
   配置流式解析、测速 204 空体、Release 不 `LogToTrace`、本机 gRPC 单连接。托管堆稳态只有约 8–17MB，这些是防涨，不是把 180 打成 20。

---

## 不要用提交大小当成绩

NVIDIA 上提交大小仍可到约 180MB，因为驱动 DLL 映射进进程。那是「提交大小」列。首页「内存」现在约 20MB。

`9f9ae41` 精简 Proto / 依赖 / 内嵌 Downloader 动的是托管侧，解释不了、也削不动提交大小；对专用工作集的贡献远小于页面卸载和修好的 Trim。
